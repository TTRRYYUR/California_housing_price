# [Bank Marketing](https://www.kaggle.com/datasets/janiobachmann/bank-marketing-dataset) — подпишет ли клиент срочный депозит

Предсказываю, откликнется ли клиент на телефонную кампанию банка и откроет депозит.
Датасет — UCI Bank Marketing, реальные кампании португальского банка.

Задача звучит просто, но в ней есть классическая ловушка.

**Лучший результат:** LightGBM — ROC-AUC 0.794, F1 0.69, accuracy 0.74 (без утечек, см. ниже).

## Про утечку `duration`

В датасете есть признак `duration` — длительность последнего звонка. С ним модель выдает AUC 0.93+ и выглядит волшебно. Проблема: длительность звонка известна только **после** того, как звонок закончился. На момент предсказания этих данных физически нет. Модель с `duration` предсказывает не «подпишет ли клиент депозит», а «долго ли с ним говорили». Это утечка.

Я убрал `duration` сразу. Все результаты ниже — честные, только на признаках, известных до звонка. Цена честности — AUC ~0.79 вместо 0.93 из туториалов, и это нормально: считаю что это реальная сложность задачи «до звонка».

## Что сделано

1. Убрал `duration`, закодировал таргет, разобрался с признаками.
2. Накатал производные признаки (закредитованность, жизненный этап, отношение баланса к возрасту).
3. Обучил три модели: LogisticRegression (бейзлайн), RandomForest, LightGBM. Гиперпараметры — `RandomizedSearchCV` по ROC-AUC.
4. Разобрал не только метрики, но и confusion matrix и permutation importance — там главное.

## Признаки

Исходные: возраст, баланс, история контактов (`campaign`, `previous`, `pdays`) плюс категории: категории баланса, маркер кредитов, баланс при возрасте, холост или в браке, пара с доходами.

Что добавил поверх:

| Признак | Идея |
|---|---|
| `balance_category` | Бины баланса: отрицательный / низкий / средний / высокий |
| `multi_loans` | Жилищный и потребительский кредит одновременно — маркер закредитованности |
| `balance_per_age` | Баланс, нормированный на возраст |
| `is_young_single` | Молодой и не в браке — отдельное потребительское поведение |
| `has_partner`, `married_with_housing` | Семейное положение и его пересечение с жилищным кредитом |

Генерация завернута в `FunctionTransformer` внутри пайплайна, чтобы кросс-валидация не текла.

Честное примечание: в топ-10 важности мои признаки не попали — сырые категории оказались сильнее. Оставил их в пайплайне как страховку и для устойчивости, но без иллюзий.

## Результаты

| Модель | CV ROC-AUC | Test ROC-AUC | F1 | Accuracy |
|---|---|---|---|---|
| LogisticRegression | 0.770 | 0.765 | 0.650 | 0.701 |
| RandomForest | 0.777 | 0.782 | 0.672 | 0.722 |
| LightGBM | **0.781** | **0.794** | **0.688** | **0.736** |

Наблюдения:

- Разрыв между моделями маленький (0.765 → 0.794). Это значит, что потолок здесь определяется признаками, а не алгоритмом — типичная история для табличных данных с сильными категориями.
- Test не проседает относительно CV ни у одной модели — переобучения нет.
- LightGBM выигрывает во всех метриках, категории (`month`, `contact`, `poutcome`) — его стихия.

## Confusion matrix: что значат ошибки

На тесте из 2233 клиентов (классы примерно сбалансированы):

| | Предсказан No Deposit | Предсказан Deposit |
|---|---|---|
| **Реально No Deposit** | 992 | 183 |
| **Реально Deposit** | 407 | 651 |

- **Precision ≈ 0.78**: из каждых 100 клиентов, которых модель отправила в обзвон как «теплых», ~78 реально подписались бы. Для кампании это совсем неплохо.
- **Recall ≈ 0.62**: мы пропускаем ~38% потенциальных вкладчиков. Это осознанная цена precision при пороге 0.5.
- Порог — это бизнес-решение, а не константа: если звонок дешевый, порог стоит опустить и добирать recall; если дорогой — поднять и бить только по самым теплым. Подбор порога под бюджет кампании — в TODO.

## Что реально драйвит предсказание (permutation importance)

- **month (~28%)** — сезонность кампаний. В одни месяцы звонят всем подряд (конверсия падает), в другие — точечно. Месяц по факту работает как прокси качества кампании, а не свойства клиента.
- **contact (~21%)** — cellular против telephone: до мобильных дозвониться и договориться проще.
- **poutcome (~18%)** — прошлый успех лучший предиктор будущего: кто уже подписывался, подпишется снова.
- **age и day (~7% каждый)**, дальше housing, pdays, balance, campaign, marital — по ~3%.

Важный вывод, который я сделал для себя: топ-признаки — это во многом **атрибуты кампании** (когда и как звонили), а не чистые свойства клиента. Модель частично учит «удачное время звонка», а не «кто клиент». Для отбора клиентов в обзвон стоит отдельно проверить модель только на клиентских признаках — это следующий шаг(TODO).

## Запуск

```bash
pip install -r requirements.txt
python main.py
```

Обучает три модели, печатает сводную таблицу, рисует ROC-кривые, confusion matrix и важность признаков, сохраняет лучший пайплайн в `best_bank_model.pkl`. `predict.py` — предсказание вероятности для нового клиента.

## Структура

```
├── data.py            # загрузка, удаление duration, кодирование таргета
├── features.py        # feature engineering (FunctionTransformer)
├── pipelines.py       # ColumnTransformer + сборка пайплайна
├── training.py        # конфиги моделей, RandomizedSearchCV, метрики
├── visualization.py   # ROC, confusion matrix, permutation importance
├── predict.py         # инференс для одного клиента
└── main.py            # оркестрация
```
